AIRGuard.Who authorized
this action?

An agent can find a convincing reason to act in a document. But the document does not get to decide what the agent is allowed to do.

AIRGuard checks proposed tool calls before they execute. It keeps the user’s authorization separate from the information an agent encounters along the way.

Guarding Agent Actions with Runtime Authority Control

Based on the October 26 revision. Earlier arXiv version ↗

01 / The problem

A normal email.
One unauthorized recipient.

The user asks an agent to send a status report to a team alias. While preparing it, the agent reads a workspace file that says an additional “compliance” address must be copied. The agent adds that address to the email.

Reading the file is relevant. Sending the report is relevant. Even the extra address has a traceable source. The missing fact is permission to disclose the report to that recipient.

We call this authority confusion: information encountered during execution is treated as permission to cause an external effect. A context-aware attack can exploit an otherwise ordinary action by changing its target or arguments.

The guard needs to answer two questions together: where did this value come from? and what permits the operation that uses it? That brings us to the work AIRGuard builds on.

02 / The landscape

Graphs and permissions
already have a history.

Agent defenses already separate control from data, track provenance, and enforce policies at tool boundaries. AIRGuard belongs to this line of work. Its contribution is a particular runtime design and an empirical study of its behavior—not the invention of graphs or access control.

Different defenses ask different questions about a proposed action. Select a lens below to see both its role and its relationship to AIRGuard.

The distinction we develop is operational: compile the task’s authority once, track how execution unfolds, and inspect concrete operations before they act. Whether this combination is better than a particular related design is an experimental question.

What does the current evidence establish about novelty?

The manuscript specifies a system that combines scoped authority, operation-level provenance, effect assessment, partial removal, and sequence audit. Its evaluation compares against ARGUS, MELON, CaMeL, and VIGIL. It does not directly compare with AuthGraph, PACE, or AGATE, and does not isolate the benefit of a unified graph with a graph-only ablation. We therefore do not claim first-ever provenance-aware authorization or superiority over every related system.

03 / The representation

The execution grows.
The authority does not.

Before the first tool call, AIRGuard compiles allowed operations from the user task and deployment policy. Retrieved documents, tool responses, packages, and skill files do not enter that compilation.

During execution, the guard builds a graph of operations. It records links to the user’s authorization and to earlier operations whose outputs supply values. These links preserve a distinction that a flat conversation can blur: knowing an address is not permission to send to it.

The graph is a record for making decisions, not a permission slip by itself. An operation may have a legitimate purpose and still carry a low-trust value. The next step is to check what that operation would actually do.

How fixed is “fixed”?

The allowed list is compiled once per trajectory. An entry without a named target binds to the first target it covers; later uses must match that target. The manuscript separately restricts external operations to targets named in the instruction. Coverage is a Boolean kind/target check; it does not include an effect or trust score. Tool-output-derived values carry low trust even if reading the source was authorized.

04 / The intervention

Catch the effect
before the tool executes.

A single call can contain several operations: multiple email recipients, a series of shell commands, or several file changes. AIRGuard splits the proposal into operations, checks their coverage and provenance, then combines risk tags, resource trust, and an effect assessment.

Sometimes it can remove an unauthorized part. Sometimes the whole call must stop. A script is especially important: the apparent job of a helper is not necessarily everything the helper will do.

For execution requests with unclear effects, a focused model can inspect the request and available script content. Its recommendation is consumed by a fixed enforcement cascade. It cannot supply a capability the user never granted.

What do “inspect,” “sandbox,” and partial removal mean here?

Only allow and audit execute in the unattended evaluations. Other decisions withhold execution; the prototype’s sandbox and quarantine labels do not establish operating-system isolation. The focused assessment runs only for process.exec and output.respond; other cases and failures use deterministic fallback rules.

Partial removal does not override an existing blocking decision, and the reduced call is not checked a second time. Sequence audit can only make the result more restrictive. These details matter: a schematic of “drop one recipient and send” is conditional, not a guarantee for every tool call.

That explains what the system is designed to do. The experiments ask a different question: what happened when it was actually used?

05 / The evidence

A safer agent still
needs to finish the task.

A defense that stops every action can have a low attack success rate and little practical value. We therefore read attack success together with benign task completion, then inspect the interventions behind those outcomes.

First, compare security and utility.

On AgentTrap, AIRGuard reduces attack success relative to no defense on all six backbones. Benign completion is preserved or improved on four. The trade-off is not uniform: it is less favorable on GPT-6 Luna and Opus 4.8.

Second, is a policy prompt enough?

We compare the full guard with a variant that puts the same policy in the agent’s prompt but does not enforce it at the runtime boundary. With GPT-5.6 Sol on 91 AgentTrap attacks, prompt-only AIRGuard has 17.6% attack success; the full system has 7.7%.

Third, what actually stopped the attacks?

We examine 74 AgentTrap runs where an attack succeeds under no defense, ARGUS, or MELON, but fails under AIRGuard on the same backbone. This is a selected diagnostic subset—not all attacks and not a component ablation.

AIRGuard intervenes in 46 of these runs. In 39, an effect check blocks execution of a script. In another 28 runs, the agent never attempts the attack and the guard takes no action. Those 28 should not be credited to an observed blocking mechanism.

The email example makes selective intervention easy to understand. The recorded analysis tells us that script-effect checks account for most observed interventions in this subset. Both belong in the story; they answer different questions.

On the 300 benign AgentTrap runs, AIRGuard blocks 27 of 1,168 tool calls and intervenes in 15 runs. Both benign runs with partial removal finish their task. That is encouraging evidence for selective handling, but too few partial-removal cases to explain aggregate utility gains on its own.

06 / What remains open

The boundary is useful.
Its precision still matters.

The results support evaluating this runtime design through security, task completion, and recorded interventions together. They do not establish that a graph alone makes an agent safe, or that one defense is best under every model and harness.

01 The guard must see the action.

AIRGuard requires a pre-action hook. Effects hidden inside a tool server or execution path that bypasses the guard fall outside that boundary. Its security objective is a design objective, not a formal verification guarantee.

02 Adapters change what gets checked.

The evaluated DTAP adapter does not extract email recipients and does not invoke the final-response hook. The email illustration must not be read as a mechanism validated by DTAP’s results.

03 Comparisons have a scope.

DTAP includes 50 direct attacks and 50 indirect injections; only the indirect group falls within the stated threat model. Across six backbones, that group records 9/300 successes without defense and 4/300 with AIRGuard. Different agent loops also confound some DTAP utility comparisons.

04 Component contributions remain open.

The paper includes a prompt-only comparison and trajectory diagnostics, not isolated ablations of the graph, selective removal, or sequence audit. Direct comparisons with AuthGraph, PACE, and AGATE are also absent. The structural differences are descriptions of design, not demonstrated superiority.

Let the agent learn from the environment.
Keep permission tied to the user’s task.

AIRGuard explores how to enforce that distinction at the moment an agent acts. The next challenge is precision: preserve useful work while identifying exactly which operation crosses the authorized boundary.
