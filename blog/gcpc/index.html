Partial Credit.What did the agent get right,
even when the task failed?

Imagine opening the Excel report an agent just produced. The result says FAIL. Before starting over, you want to know: what can I keep, and what still needs fixing?

We build a checklist from the task’s instructions and verifier, then look for evidence for each requirement in the execution record. This article explains how—and lets you inspect the checklists yourself.

01 / Why look beyond pass rate?

Both runs failed. Did they do the same work?

01 / Same verdict

Here are two runs of the same task. The agent has to turn a population PDF and an income spreadsheet into one Excel report. One run could read an xlsx skill; the other could not. The official verifier rejected both.

02 / Open the verdict

Before it says FAIL, the verifier runs 26 checks. Lay them out and the two runs stop looking alike. The run with the skill passes more of the checks—but neither run passes them all.

03 / One shared error

So why did both fail? One column. The task calls it Quarter, but it means income quartile: each region should be labelled Q1 to Q4 by its median income. Both reports contain the string nan where those labels should be. Nothing else either run did cancels that error.

04 / Different files

Both runs used pandas to group and sum the data. Without the skill, the agent wrote those sums into ordinary cells. After reading the xlsx guide, the other run built what Excel recognizes as a PivotTable: a source-data connection, a pivot cache, and row and value fields. The verifier finds those objects in one file and not the other.

05 / A different unit

But a test count is not the whole story. Eight of the tiles check that eight columns exist in the source-data sheet. In the archived checklist, these checks support one requirement, S-06. Meanwhile, an aggregation check confirms that the operation is a sum, but not which field is being summed. A tile count depends on how someone split the tests.

06 / Start from the task

A final FAIL hides what was done. A test count depends on how the tests were written. We want the task’s own list of requirements, with evidence for each one. Here are the nine requirements in this task’s archived checklist. The rest of this article explains how we construct and evaluate such a list.

Which requirements are met, which are not,
and what evidence supports each judgment?

What one pair can and cannot show

This single pair does not establish a causal or population-level skill effect.

Read the limits of this comparison

Passing structural checks does not prove all numbers are correct. The invalid Quarter value is observed; its name is not established as the cause.

A check is one executable verifier test; a requirement describes requested work. Their counts are not interchangeable, and the nine requirements are not a one-to-one regrouping of all 26 tests. No requirement judgments are inferred here. A verifier’s SKIPPED status is distinct from GCPC’s Abstain.

02 / Completion

What should count as a unit of progress?

A requirement starts with what the user asked for. “Create a population pivot” means more than placing a table in a file: it must group the right regions and sum the right values. Our evaluation should preserve that meaning, whichever valid implementation the agent chooses.

The same distinction applies to income groups. A check can confirm that every label is Q1–Q4 without confirming that each region belongs in the assigned group. A requirement and the evidence used to verify it must be inspected together.

Each requirement needs a source and a way to check it. Unless the task demands a particular library or button, using that library or button is not an achievement in itself. Different valid solutions must remain possible.

Why counting the same condition twice changes the score

The same discipline applies to redundancy. “Create a native pivot table” and “the workbook contains that native pivot object” may count the same condition twice. Repeating a satisfied condition raises its effective weight. Organizing requirements into categories helps us inspect coverage, but does not by itself remove duplicates or settle the right granularity.

So the contribution is not simply replacing PASS/FAIL with more boxes. It is a procedure for constructing and evaluating task-grounded boxes whose meaning and evidence can be inspected.

A stronger requirement still needs evidence

Writing a fuller requirement does not repair an incomplete verifier.

See the limits recorded for S-02 and S-07

In the archived checklist, S-02 and S-07 explicitly note these verifier limitations, but their linked verification procedures still inherit them. Stating a stronger requirement in natural language is not the same as implementing a stronger check. A missing check must be supplied, or the available evidence must support the judgment.

Sources: the archived sales-pivot-analysis verifier and checklist of nine requirements; paper, Method.

03 / Checklists

How do we turn a task into a checklist?

Writing a careful checklist from scratch for every task is expensive. Asking a model to invent one freely is easier, but can produce repeated requirements, omitted requirements, or restrictions the task never asked for. We divide the work: people specify reusable rules, and a model applies those rules to each task.

Choose a requirement below. Can you trace it back to something the user actually requested?

The generator receives the task instruction and verifier source. It does not receive the evaluated trajectories, their outcomes, or a reference solution. Each proposed requirement must be self-contained, avoid redundant requirements, and carry an exact quotation from the task instruction.

How five categories help inspect coverage

Comprehension, acquisition, computation, construction and validation help audit coverage and describe failure types. In the paper’s production procedure, they are not five mandatory sequential stages, and they are not an input template for checklist generation. Putting two repeated requirements in the same category does not make them non-redundant.

How do we keep that link when we scale to hundreds of tasks?

What is checked before the checklist is frozen?

The validator checks that the source quotation occurs in the task, the referenced verifier test exists, and the requirement describes a task requirement. Passing these gates establishes traceability, not complete semantic correctness.

People review the checklist for missing requirements, repeated requirements and conditions the task never asked for. The reviewed checklist is then frozen and reused for every evaluated run of that task.

Manual-review scope: an unresolved detail

The author’s account used for this article is that every generated checklist received manual review before scoring, and reviewers could consult execution records for plausibility. The current paper describes targeted author review. These descriptions remain unresolved. We do not claim that manual review was blind to trajectories.

Once a requirement has a source, where should its evidence come from?

A checking plan is not a test result

A generated verification plan is not proof that a new test was implemented or run.

What validation and review still leave unresolved

Automatic validation checks traceability, not completeness. Human review remains necessary; the recorded scope of that review is an unresolved protocol detail.

With the checklist frozen, the next step is to look at what each run actually accomplished.

Source: paper, checklist synthesis.

04 / Evidence

How do we grade a requirement?

A separate judge reads one execution record against the frozen checklist. It looks at tool outputs and visible file contents, then assigns one of three labels to each requirement.

If no requirement is decidable, we report a zero-evidence case, not a perfect score.

A high score with low coverage can be misleading: the visible record may support only a small part of the task.

The official verifier may see things missing from the log. We therefore keep two versions separate: plain GCPC uses log evidence only; GCPC with official outcome also incorporates the final PASS or FAIL through fixed rules.

How an official PASS or FAIL changes the calculation

On an official PASS, assertion-route requirements are set to Yes because the referenced tests have passed. On FAIL, existing requirement judgments remain unchanged: the final binary outcome alone does not identify the failed requirements. The script also adds one final-outcome entry, Yes for PASS or No for FAIL.

For example, nine log-supported Yes judgments and an official FAIL give plain GCPC 9/9, but the outcome-inclusive version 9/10. This bookkeeping reconciles the score with the final outcome; it does not independently validate the evaluator. Outcome-free and outcome-inclusive scores must not be presented as the same measurement.

We now have a requirement-by-requirement account of the run. The next question is whether people find that account informative.

Source: paper, trajectory scoring and metrics.

05 / Validation

Does the checklist tell us something useful?

A plausible pipeline is not enough. We evaluated it on a deduplicated population of 4,455 SkillsBench trajectories, compared scoring procedures, and collected human judgments. Two findings connect most directly to the question we started with.

First: agreement with human comparisons.

Five annotators evaluated a prespecified set of 96 trajectories from 12 tasks across all eight SkillsBench domains. They rated overall progress and compared same-task trajectories before seeing the checklist. This kept those judgments separate from the requirements used by our method.

The chart measures agreement with people’s preferences, not task success. A separate measure—correlation with human progress ratings—was 0.382 for GCPC and 0.218 for the holistic judge.

Second: the changes hidden inside FAIL → FAIL.

We matched runs by task, harness, and model-and-source configuration. Among 1,946 with/without-skill pairs, many failed in both conditions. Does that shared verdict mean nothing changed? Switch the view below.

Final pass rate misses changes in both directions. The checklist makes those differences inspectable; it does not show that skills always help.

Where does the record stop helping?

A checklist is only as informative as the evidence it can see. Transfer to other benchmarks makes that boundary clear.

The same pipeline was applied to Terminal-Bench and SWE-bench without changing its prompts or scoring rules. Terminal-Bench supplied useful diagnoses: in the paper’s pypi-server example, a failed run satisfied four of six requirements but did not build the distributable artifact or start the package-index server.

SWE-bench exposed the opposite case. Of 74 decidable resolved/unresolved pairs, 58 received the same log-only GCPC score, and 42.1% of requirements received Abstain. When decisive evidence lives outside the visible log, the checklist cannot recover it by asking more questions.

What these results establish—and what they do not

The study tests informativeness on its sample; it does not establish universal superiority.

Read the comparison, sampling and causal limits

The 4,455-trajectory analysis population differs from the archived run collection in the task browser.

Human agreement is measured on the studied sample. Comparable-pair counts differ by method because of ties and missing scores; the chart reports point estimates. These results do not establish universal superiority or that every generated requirement is correct.

The paired-failure distribution is observational, not a causal skill-effect estimate. Its middle share is the remainder of two rounded percentages and includes small positive and negative changes.

We also have not established that GCPC outperforms simply aggregating all available verifier subtests: that direct baseline is absent from the main reported comparison. Where reliable executable checks already exist, they remain valuable evidence. Checklist provenance, human review and finer granularity do not guarantee completeness or eliminate judge error.

Keep the final verdict.
Make the completed work—and the uncertainty—visible.

That is the role of checklist-based partial credit: a task-grounded, inspectable account of what an agent accomplished, what remains unmet, and what the record does not let us decide. The pipeline makes that account easier to construct across tasks; the empirical study tests how informative it actually is.

Sources: paper, Experiments (human evaluation, matched skill analysis, cross-benchmark transfer) and the full paper.
