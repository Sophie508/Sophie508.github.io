Partial Credit.What did the agent get right,
even when the task failed?

Two agent runs can fail the same task after completing very different amounts of work. A final PASS or FAIL tells us whether the result was accepted. It does not tell us which requirements were met.

We build a checklist from the task’s instructions and verifier, then look for evidence for each requirement in the execution record. This article explains how—and lets you inspect the checklists yourself.

01 / Why look beyond pass rate?

Both runs failed. Did they do the same work?

Consider a task that asks for an Excel report with four pivot tables. We compare two runs of the same task, with and without an xlsx skill. Both receive a final FAIL.

The agent must match a population PDF to an income spreadsheet using each region’s code, SA2_CODE. The output is one Excel file: a joined source-data sheet and four pivot tables.

For Population by State, the question is simply: how many people live in each state? Group the regions by STATE, then add their POPULATION_2023 values. The other tables count earners, count regions, and group earners by state and income quartile.

What makes a table an Excel PivotTable?

An ordinary summary can contain just the computed numbers in cells. An Excel PivotTable also stores its data source and field settings: which field groups the rows, which field groups the columns, and which values to sum or count. Excel can recognize and manipulate that structure. The diagrams below show these stored structures, not a verified live Excel session.

Both runs use Python and pandas. Without a skill, the agent groups and sums the data, then writes those results into ordinary cells. After reading the xlsx guide, the other run creates structures that Excel recognizes as PivotTables, including their source-data connection and field settings.

The official verifier detects this difference. It cannot find the required PivotTables in the first file. In the second, it finds them and the tested row fields and aggregation settings pass. That establishes a structural difference; it does not prove every reported number is correct.

Both reports still contain the string nan in Quarter, the income-group column. Despite its name, this column means income quartile, not calendar quarter: regions must be assigned Q1, Q2, Q3 or Q4 based on median income. Both therefore fail the overall verifier. Creating a native pivot object does not cancel out that error.

Yet the same final FAIL conceals different sets of satisfied requirements. The question becomes:

Which requirements are met, which are not,
and what evidence supports each judgment?

The official subtests already recover part of this information. GCPC asks a further question: how can we organize evaluation around task requirements, show how each requirement can be checked, and distinguish unmet requirements from missing evidence?

This pair illustrates the distinction; it does not establish a causal or population-level skill effect. Verifier subtests vary in granularity, and pytest’s “skipped” status is not GCPC’s Abstain.

02 / Completion

        
What should count as a unit of progress?

        
The verifier above already distinguishes the two runs: 12 tests pass without the skill, and 22 pass with it. So why build a checklist? Because a test count depends on how the code was split up—and may leave parts of the requested work unchecked.

      

      
      

        
Coverage matters, too. The population pivot must sum POPULATION_2023, but its aggregation test checks that the operation is sum without independently checking which numeric field is summed. The Quarter test checks allowed labels, not whether each region was assigned to the correct income quartile. These are specific limits of the existing tests, not evidence that all automated verification is inadequate.

        

          Does the generated checklist fix those gaps?
          
Not automatically. In the archived checklist, S-02 and S-07 explicitly note these verifier limitations, but their linked verification procedures still inherit them. Stating a stronger requirement in natural language is not the same as implementing a stronger check. A missing check must be supplied, or the available evidence must support the judgment.

        

        
This is why our starting point is the task requirement. Each checklist item should describe a requested outcome, identify its source, and explain how it can be checked. It should allow different valid solutions. Unless the task requires a particular library or button, using that library or button is not itself a completion criterion.

        
Why not add more and more checklist items?
The same discipline applies to redundancy. “Create a native pivot table” and “the workbook contains that native pivot object” may count the same condition twice. Repeating a satisfied condition raises its effective weight. Organizing items into categories helps us inspect coverage, but does not by itself remove duplicates or settle the right granularity.

        
So the contribution is not simply replacing PASS/FAIL with more boxes. It is a procedure for constructing and evaluating task-grounded boxes whose meaning and evidence can be inspected.

        
Sources: the archived sales-pivot-analysis verifier and nine-item checklist; paper, Method.

      

    

    

      

        
03 / Checklists

        
How do we turn a task into a checklist?

        
Writing a careful checklist from scratch for every task is expensive. Asking a model to invent one freely is easier, but can produce repeated items, omitted requirements, or restrictions the task never asked for. We divide the work: people specify reusable rules, and a model applies those rules to each task.

        
Below, choose a task and open a requirement. The highlighted words show where that requirement comes from.

        
The generator receives the task instruction and verifier source. It does not receive the evaluated trajectories, their outcomes, or a reference solution. Each proposed item must be self-contained, avoid redundant requirements, and carry an exact quotation from the task instruction.

      

      
      
Doing this for hundreds of tasks requires more than a good prompt. People set the rules, the model drafts task-specific items, and validation and review happen before the checklist is frozen.

      
      

        
Every item also says how it could be checked. Most reuse a test that already exists; some identify a missing executable check; a small fraction require judgment.

      

      
      
What do the automatic validation gates check?
The validator checks that the source quotation occurs in the task, the referenced verifier test exists, and the item describes a task requirement. Passing these gates establishes traceability, not complete semantic correctness.

        
People review the checklist for missing requirements, repeated items and conditions the task never asked for. The reviewed checklist is then frozen and reused for every evaluated run of that task.

        
Who could see trajectories during review?
The generator does not receive evaluated trajectories. According to the author’s account, human reviewers checked every checklist before scoring and could consult execution records to check whether conditions were plausible in the environment. They were not meant to remove a valid requirement because an agent failed it. The paper currently describes targeted review; this scope needs reconciliation before publication.

        

          What do the five categories do?
          
Comprehension, acquisition, computation, construction and validation help audit coverage and describe failure types. In the paper’s production procedure, they are not five mandatory sequential stages, and they are not an input template for checklist generation. Putting two repeated requirements in the same category does not make them non-redundant.

        

        
This reduces repeated manual authoring. It does not eliminate review: whether new tasks can safely use less review remains an empirical question. With the checklist fixed, we can now ask what each run actually accomplished.

        
Source: paper, checklist synthesis. The manual-review scope above reflects the author’s account of the workflow; see the draft’s protocol note.

      

    

    

      

        
04 / Evidence

        
How do we grade a requirement?

        
After the checklist is fixed, a separate judge reads one trajectory and evaluates each item. Displayed tool outputs and file contents count as evidence. An agent’s claim that it completed the work, or a state that never appears in the log, does not establish success.

        
For every requirement, the judge must separate three situations: evidence that it was met, evidence that it was not met, and too little evidence to decide.

      

      
      
      

        
The score answers “how much of the work we can judge was done?” Coverage answers “how much of the work can we judge at all?” A high score with low coverage should not be read as near-complete success. If nothing can be judged, we report a zero-evidence case, not a perfect score.

        
The official verifier may see things missing from the log. We therefore keep two versions separate: plain GCPC uses log evidence only; GCPC with official outcome also incorporates the final PASS or FAIL through fixed rules.

        

          How is the official outcome incorporated?
          
On an official PASS, assertion-route items are set to Yes because the referenced tests have passed. On FAIL, existing item judgments remain unchanged: the final binary outcome alone does not identify the failed requirements. The script also adds one endpoint item, Yes for PASS or No for FAIL.

          
For example, nine log-supported Yes judgments and an official FAIL give plain GCPC 9/9, but the outcome-inclusive version 9/10. This bookkeeping reconciles the score with the final outcome; it does not independently validate the evaluator. Outcome-free and outcome-inclusive scores must not be presented as the same measurement.

        

        
We now have a requirement-by-requirement account of the run. The next question is whether people find that account informative.

        
Source: paper, trajectory scoring and metrics.

      

    

    

      

        
05 / Validation

        
Does the checklist tell us something useful?

        
A plausible pipeline is not enough. We evaluated it on a deduplicated population of 4,455 SkillsBench trajectories, compared scoring procedures, and collected human judgments. This analysis population differs from the archived run collection in the task browser. Two findings connect most directly to the question we started with.

        
First: agreement with human comparisons.

        
Five annotators evaluated a prespecified set of 96 trajectories from 12 tasks across all eight SkillsBench domains. They rated overall progress and compared same-task trajectories before seeing the checklist. This kept those judgments separate from the criteria used by our method.

      

      
      

        
GCPC agreed with human pairwise preferences 73.0% of the time, compared with 61.3% for the holistic judge. Its correlation with human progress ratings was also higher in this study: 0.382 versus 0.218. These are different measures—73.0% is preference agreement, not a correlation or a task-success rate.

        
This supports the usefulness of requirement-level evaluation on the studied sample. It does not establish that every generated criterion is correct or that the same advantage will hold for every task distribution.

        
Second: the changes hidden inside FAIL → FAIL.

        
We constructed 1,946 with/without-skill pairs matched by task, harness, and model-and-source configuration. Of these, 879 pairs failed in both conditions. Within that group, 20.9% improved by more than 0.10 in the paper’s checklist score, while 18.7% regressed by more than 0.10. The median change was zero.

      

      
      

        
Final pass rate misses changes in both directions. The checklist makes those differences inspectable; it does not show that skills always help.

        
Where the approach stops.

        
The same pipeline was applied to Terminal-Bench and SWE-bench without changing its prompts or scoring rules. Terminal-Bench supplied useful diagnoses: in the paper’s pypi-server example, a failed run satisfied four of six criteria but did not build the distributable artifact or start the package-index server.

        
SWE-bench exposed the opposite case. Of 74 decidable resolved/unresolved pairs, 58 received the same log-only GCPC score, and 42.1% of criteria received Abstain. When decisive evidence lives outside the visible log, the checklist cannot recover it by asking more questions.

        
We also have not established that GCPC outperforms simply aggregating all available verifier subtests: that direct baseline is absent from the main reported comparison. Where reliable executable checks already exist, they remain valuable evidence. Checklist provenance, human review and finer granularity do not guarantee completeness or eliminate judge error.

        
Keep the final verdict.
Make the completed work—and the uncertainty—visible.

        
That is the role of checklist-based partial credit: a task-grounded, inspectable account of what an agent accomplished, what remains unmet, and what the record does not let us decide. The pipeline makes that account easier to construct across tasks; the empirical study tests how informative it actually is.

        
Sources: paper, Experiments (human evaluation, matched skill analysis, cross-benchmark transfer) and the full paper.

        

          Draft protocol note: manual-review scope
          
The author’s account used for this article is that every generated checklist received manual review before scoring, and reviewers could consult execution records for plausibility. The current paper describes targeted author review. These descriptions need to be reconciled before publication; this draft does not claim that manual review was blind to trajectories. No unverified personal correction anecdote is included.
