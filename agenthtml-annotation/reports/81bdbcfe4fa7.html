TerminalBench/terminal_devops/case 01

The sanitizer read a comment. The browser read an image.

A recorded agent run against a deliberately weak XSS filter. Thirty rewrites of one file, and the winning move was not a cleverer payload — it was finding the single byte string that the HTML parser and the sanitizer disagree about.

/app/out.html — final, after filtering <!--><img src=x onerror="alert('XSS Bypass!')">-->
01

The brief

/app/filter.py takes an HTML file as its argument and rewrites it in place, stripping JavaScript so the page can no longer run any. The task: leave behind an /app/out.html that, after that rewriting, still fires an alert() in a browser — with no click, no hover, no input.

Verification is the task's own script, /app/test_outputs.py. The agent read both files first, then summarised the filter's three defences from the source.

What the filter removes

rule 01 — element
<script>

Every script element, regardless of its type.

rule 02 — element
<iframe> <frame> <object> <embed>

The embedding elements that could pull in someone else's document.

rule 03 — attribute
on*

Any attribute whose name begins with on — onload, onerror, onmouseover. Matched case-sensitively on the name, against parsed element tags.

The gap. All three rules walk element tags, because the filter parses with BeautifulSoup and iterates over parsed tags. Anything the parser stores as a comment node is never an element tag — so it is never inspected, never edited, and is written back out byte for byte.

03

Same bytes, two readers

The payload is not encoded, obfuscated, or split. It is plain text that the two parsers simply read differently. Switch readers to see the same string tokenised the way each one sees it.

<!--><img src=x onerror="alert('XSS Bypass!')">-->
what the filter does with it One Comment node, start to finish. The rules above iterate element tags; a comment is not a tag, so its interior is never examined. Nothing inside is removed or rewritten. It is serialised back to disk unchanged — which is why onerror is still present in the filtered file.
<!--> <img src=x onerror="alert('XSS Bypass!')">-->
what the browser does with it The tokenizer enters comment-start, reads !--, then hits > immediately. That is an abrupt-closing-of-empty-comment parse error: the comment ends at once, empty. The next characters are no longer inside anything — <img src=x onerror=…> becomes a real element. The image source x fails to load, the error handler fires, and alert() runs with no user interaction.
exact bytes written <!--><img src=x onerror="alert('XSS Bypass!')">-->

Where the trap was. The agent had already reasoned, on the way in, that <!--> would not close a comment — HTML comments end with -->, not >. That intuition is what HTML authors expect and what many sanitisers assume; the tokenizer spec says otherwise for this exact degenerate sequence. The run's own commentary flips on this point between steps s108 and s114. The recorded proof is the passing test, not a browser trace.

The receipt

Colophon

A case report on an authorised, sandboxed benchmark task. The payload is shown because the target filter is a toy built for this exercise and the run is over; it is not a technique to carry anywhere real, and against any sanitiser that parses untrusted HTML as data it does nothing at all.

Two voices, one sheet — machine set in mono, narration in serif, on cool spec-grey; alert-red for the one thing that executed, highlighter amber for what merely survived.
