The task

Old-style Parent.func(arg) must keep its argument

pyupgrade rewrites the pre-super() calling convention Parent.func(arg) into super().func(...). For instance methods the first argument is self and is correctly dropped; for static methods the first argument is a real argument and must be preserved. The agent was told to reproduce the bug first and re-run the repro after fixing it.

Reproduction script the agent wrote

/pyupgrade/reproduce.py — created with create, then filled with the issue's snippet
class Parent:
    @staticmethod
    def func(arg):
        return 0

class Child(Parent):
    @staticmethod
    def func(arg):
        return Parent.func(arg)

print(Child.func(1))
⚠ This script cannot detect the bug. func unconditionally return 0, so the output is 0 with or without the argument. It never runs pyupgrade over the file and never inspects the rewritten source — the only place the defect is visible.

Where the rewrite is wired up

/pyupgrade/pyupgrade/_plugins/legacy.py — visit_Module, observed at lines 188–195
super_func = functools.partial(
    find_and_replace_call, template='super()')
for offset in visitor.super_offsets:
    yield offset, super_func

for offset, func_name in visitor.old_super_offsets:
    template = f'super().{func_name}({{rest}})'
    callback = functools.partial(
        find_and_replace_call, template=template)
    yield offset, callback

The old-super template is built from the attribute name and only splices in {rest} — everything after the first argument. The detection in visit_Call accepts a static-method call because the first argument matches the function's first parameter, but no static-method distinction is carried into the template. That is the actual bug locus; the agent edited _token_helpers.py instead.

Why it failed

Four compounding errors

None of these are exotic; each one is a plausible next step that nonetheless cannot move the task forward.

🔍

1 · The oracle was blind

The repro executes the original file and prints a constant. The defect only exists in pyupgrade's output text. A valid repro had to run the tool over the file and diff the rewritten source (or call the token helpers directly). Everything downstream inherited this flaw: three runs, three meaningless passes.

✍️

2 · The edits targeted the wrong layer

The argument is dropped because legacy.py builds the template super().{func_name}({rest}) without knowing whether the method is static. The agent kept editing the generic token-parsing layer, which has no knowledge of static methods at all, so no local change there could express the fix.

🔄

3 · A no-op was mistaken for progress

Edit A changed indentation and whitespace. Edit B added a branch that provably cannot be taken. The agent's narration describes both as functionally significant, and because the (blind) test kept returning the same value, nothing contradicted the narration.

🚫

4 · Unnoticed duplicate application

Re-issuing an identical range edit inserted the same block again, creating three stacked copies separated by early returns. The line count grew 518→522→526→530 and the agent read each “File updated” message as success rather than checking the region it had just written.

Why the reproduction script could not fail +

The bug is a source-to-source rewrite: pyupgrade parses Parent.func(arg) and emits text. Executing reproduce.py without running pyupgrade over it therefore tests nothing. The agent's script returns the literal 0 from both methods, so print(Child.func(1)) emits 0 in the buggy and fixed worlds alike. A discriminating check would run pyupgrade on the snippet and assert the rewritten text contains super().func(arg), or exercise parse_call_args / find_and_replace_call against token streams directly. This is the single root cause of the run's inability to tell progress from stagnation.

Is the parse_call_args guard truly unreachable? +

In parse_call_args, arguments are appended when a top-level comma is seen, and the final argument is appended inside the closing-brace branch whenever the span's source is non-blank. So for f(arg) the list is already [(arg_start, i)] and not args is false; for f() the appended source is blank and the new guard's own .strip() test is also false. Either way the added block never runs. That is consistent with the recorded observation: behaviour and output were unchanged after it was applied.

Uncertainty in this reconstruction +

Two things are read from the recorded artifacts rather than stated outright. First, the exit status string is submitted (exit_context) while no submit command occurs in the transcript and the final edit has no observing result — the run was closed by the harness's exit condition, and this report treats the patch as the mid-loop working tree, not as a deliberate submission. Second, the exact upstream fix is not present in the case data (target and eval_logs were stripped), so the root-cause description of the legacy.py template is an inference from the observed source, not a comparison against a reference patch.
