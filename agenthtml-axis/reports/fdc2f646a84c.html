The defectissue #545

Legacy-super rewriting assumes the first argument is self

The issue statement is one sentence long: rewriting old-style superclasses removes arguments for static methods.

class Parent:
    @staticmethod
    def func(arg):
        return 0

class Child(Parent):
    @staticmethod
    def func(arg):
        return Parent.func(arg)

pyupgrade rewrites  Parent.func(arg)  →  super().func()  (should be super().func(arg))

In pyupgrade/_plugins/legacy.py, the visitor detects base.name(first_arg, …) when the first argument matches the enclosing function's first parameter, records it as an old-style superclass call, and visit_Module builds the replacement as super().{name}({rest}). Downstream, replace_call derives rest starting after the first argument. That is correct for an instance method, where argument zero is self and disappears into super() — and wrong for a @staticmethod, where argument zero is a real argument that gets silently discarded.

A fix therefore has to reach the detection logic in legacy.py — the place the agent identified but never edited. It opened that file twice, then moved on and edited a different module entirely.

Why the repeated edit could never work

The three identical edits append this to parse_call_args:

# Always include the first argument
if not args and tokens_to_src(tokens[arg_start:i]).strip():
    args.append((arg_start, i))

For the call in question, Parent.func(arg), parse_call_args already returns exactly one argument — so not args is false and the new branch never executes. The guard only fires on a zero-argument call, which is the case that was never broken. Even a branch that did fire would not help: replace_call builds rest from args[0][1] + 1 regardless, so argument zero is dropped by the caller, not the parser.

The earlier edit at turn 11 is the same story in a different register: the narration says "let's edit the function to always include the arguments," and the edit itself only re-indents the signature of find_and_replace_call from the project's 8-space continuation style to 4, plus one whitespace tweak in Tuple[int, ...]. Stated intent and applied change have nothing to do with each other.
