Diagnosis

The guard was not the only problem.

The generated patch contains a plausible instinct—don’t install into an existing environment—but implements it with an unreliable string check and a global behavior change.

Evidence against the patch

  • revision is always non-null by line 156.When omitted, line 126 assigns conf.branches[0]. The guard can no longer distinguish a user-supplied revision from the default.
  • --python=same is not proven equal to "existing".The patch relies on a raw env_spec string instead of the already-imported is_existing_only(environments) behavior.
  • Project installation is removed unconditionally.The final diff deletes env.install_project even for managed environments that can and should install the requested revision.
  • The verification path may be stale.Nine unchanged runs after source edits strongly suggest the shell command may not have executed the checkout, though the trace never confirms this.

Most likely repair seam

Preserve whether revision was explicitly supplied. Branch on environment capability, not an option spelling.

This is an inference from the recorded source and behavior, not a verified replacement patch. The trajectory contains no passing test or evaluation log; those fields were stripped from the case.

Clean handoff

  1. Reproduce with the edited checkout explicitly, not an unknown installed asv entry point.
  2. Capture whether revision was supplied before assigning the default branch.
  3. Use the resolved environments’ capabilities—or is_existing_only—for control flow.
  4. Skip install_project only for environments that cannot install; preserve managed-environment behavior.
  5. Add focused tests for both -E existing and --python=same, plus a managed environment with an explicit revision.
